\section{Introduction}
\label{sec:intro}

Deep reinforcement learning (RL) enables agile motor control in robotics~\cite{hwangbo2019learning, rudin2022advanced}. While transferring physics-trained controllers to compute-heavy robots with Linux and ROS~2 is well established~\cite{mittal2023orbit}, deploying policies to resource-constrained microcontrollers (MCUs) such as the ESP32 ($<$520\,kB RAM, no OS) remains entirely manual. Developers must hand-code network weights into C arrays, implement forward inference kernels, and rewrite peripheral drivers whenever model architectures or hardware pins change.

To address this gap, we present \texttt{simtoreal}, an open-source Python library that automates policy deployment to microcontrollers. Our contributions are: (1)~a dual-target code exporter converting trained Stable-Baselines3 or PyTorch actors into zero-allocation C headers or precompiled MicroPython bytecode (\texttt{.mpy}); (2)~a hardware abstraction synthesizer generating the complete on-board control loop (\texttt{main.py}) from a declarative YAML specification; and (3)~empirical benchmarking of numerical equivalence, embedded resource overhead on an ESP32, and dynamic self-righting on a 2-DOF bipedal robot (\textit{Robo1}).

\section{Literature Review}
\label{sec:lit_review}

\textbf{Sim-to-Real Transfer:} The discrepancy between simulation and the real world (the reality gap) is primarily addressed via domain randomization (DR)~\cite{tobin2017domain} and actuator system identification~\cite{hwangbo2019learning, tan2018sim}. While modern simulators enable large-scale DR training~\cite{rudin2022advanced, mittal2023orbit}, standard deployment runtimes (ONNX, TorchScript) require tens of megabytes of RAM, far exceeding MCU limits.

\textbf{Embedded Machine Learning (TinyML):} Frameworks such as TensorFlow Lite for Microcontrollers (TFLM)~\cite{david2021tensorflow} and MCUNet~\cite{lin2020mcunet} support MCU inference, but focus on vision and audio tasks with general tensor interpreters that add needless overhead for compact control MLPs. RLtools~\cite{eschmann2023rltools} enables embedded C++ execution, but requires training within its custom C++ environment, hindering direct reuse of standard Python RL ecosystems (Gymnasium, Stable-Baselines3).

\textbf{Benchmarking Embedded Sim-to-Real:} Zhou et al.~\cite{zhou2026measure} demonstrated that low-cost edge platforms suffer substantial performance degradation without grounded benchmarks. We therefore evaluate numerical parity, closed-loop simulation consistency, and embedded microcontroller resource limits.

\section{Materials and Methods}
\label{sec:methodology}

The \texttt{simtoreal} pipeline (Fig.~\ref{fig:architecture}) automates the translation of simulation-trained policies into functional embedded firmware through three main stages.

\textbf{1) Policy Extraction:} The framework parses trained Stable-Baselines3 PPO models (\texttt{.zip}) or PyTorch checkpoints (\texttt{.pt}), extracting layer weights $\mathbf{W}_l$, biases $\mathbf{b}_l$, and activations ($\tanh$, $\text{ReLU}$). Critic networks and optimizer states are discarded, isolating the forward actor graph.

\textbf{2) Dual-Target Code Generation:} Network parameters can be exported via two distinct backends:
\emph{a)~Zero-Heap C Header:} Parameters are exported as compile-time \texttt{const float} arrays stored in Flash. Forward inference runs in \texttt{policy\_forward()} via two statically allocated stack buffers that alternate ping-pong style. Dynamic heap allocation (\texttt{malloc}) is entirely avoided, preventing runtime memory fragmentation.
\emph{b)~Precompiled MicroPython Bytecode:} To support rapid prototyping, policies can be exported as MicroPython modules and precompiled to \texttt{.mpy} bytecode via \texttt{mpy-cross}, eliminating on-device memory exhaustion during source parsing.

\textbf{3) Control Loop Synthesis:} Peripherals and execution parameters are declared in \texttt{config.yaml}. The generator writes \texttt{main.py}, configuring sensor drivers (MPU-6050 over I2C), affine observation normalization ($\mathbf{o}_t = \mathbf{s} \odot \mathbf{x} + \mathbf{b}$), actuator mapping (\texttt{delta} or \texttt{absolute} modes with angle limits), and an accurate 50\,Hz periodic control loop.

\textbf{4) Experimental Testbed (Robo1):} We evaluated the framework on \textit{Robo1} (Fig.~\ref{fig:robo}), a 2-DOF self-righting robot (total mass 94.8\,g) with an ESP32 MCU, an MPU-6050 IMU, and two SG90 micro-servos. A matching digital twin was built in MuJoCo using exact CAD masses, spatial inertia tensors, joint limits ($\pm 90^\circ$), damping ($0.02$\,N$\cdot$m$\cdot$s/rad), and collision proxies. The observation vector is $\mathbf{o}_t = [\phi_{\text{roll}}, \theta_{\text{pitch}}, a_z, q_1, q_2]$, where $a_z$ disambiguates upright from inverted orientations, and $q_1, q_2$ represent current joint angles. Actions apply incremental target adjustments ($\Delta q \le 0.08$\,rad) at 50\,Hz. Training incorporates domain randomization over mass ($\pm15\%$), damping/friction ($\pm20\%$), actuator gain ($\pm15\%$), and sensor noise ($\sigma = 0.015$\,rad).

\section{Results and Discussion}
\label{sec:results}
\enlargethispage{2.0\baselineskip}

The framework was benchmarked across numerical precision, simulation fidelity, and microcontroller resource overhead (Table~\ref{tab:verify}). The evaluated policy is a 5--64--64--2 $\tanh$ MLP (4{,}674 parameters, 18.7\,kB as float32).

\textbf{Numerical Equivalence and Simulation Fidelity:}
Across 4{,}609 host test inputs (2{,}000 random vectors and 2{,}609 state samples from simulation), maximum absolute difference against PyTorch was $1.2\times10^{-6}$ for MicroPython and $2.9\times10^{-6}$ for C, confirming single-precision floating-point agreement. Action sign and magnitude agreement was 100\%. 

In closed-loop MuJoCo simulation over 1{,}000 episodes across five initial fallen poses, the synthesized C controller produced righting trajectories identical to PyTorch. Across nominal and domain-randomized physics, the policy achieved a 97.2\% overall get-up success rate (100\% from standard fallen poses in 1.15\,s mean; 88.0\% from severe inverted poses). Under randomized dynamics, success remained at 97.2\% with a modest 20\% increase in righting time ($1.38$\,s), confirming high dynamic robustness.

\textbf{Microcontroller Resource and Latency Profile:}
On an ESP32 running MicroPython 1.28, the precompiled \texttt{.mpy} policy matched PyTorch outputs within $9.5\times10^{-7}$. The compiled binary occupies 75.1\,kB in Flash. In RAM, MicroPython object representations allocate 119.6\,kB of dynamic memory (72\% of the 162.3\,kB free heap). 

On-device timing indicates that MicroPython inference requires $155.2 \pm 7.4$\,ms per decision. In bench tests with sensors and servos connected, reading the MPU-6050 over I2C takes 3.2\,ms and servo PWM updates require 0.95\,ms. Total hardware I/O requires only 4.2\,ms, easily fitting within the 20\,ms (50\,Hz) real-time budget. However, because MicroPython software inference takes $\sim$182\,ms under full loop memory management, the complete interpreted loop runs at 5.4\,Hz. Static sensor noise was measured at 1.3--1.6\,mrad (0.2\,mrad with complementary filtering), well within the 15\,mrad noise injected during training. These benchmarks show that while MicroPython is effective for rapid prototyping, compiled C header deployment is essential for achieving real-time 50\,Hz control.

\section{Conclusion}
\label{sec:conclusion}

The \texttt{simtoreal} framework bridges standard Python reinforcement learning tools and resource-constrained microcontroller deployment. By combining automated policy extraction, zero-heap C and MicroPython code generation, and declarative control loop synthesis, it eliminates manual firmware translation. Empirical evaluations confirm numerical parity and 97.2\% simulation get-up success on the \textit{Robo1} bipedal testbed. Microcontroller profiling demonstrates that peripheral I/O easily satisfies 50\,Hz deadlines, while highlighting software-interpreted inference as the key performance bottleneck. Future work entails deploying the compiled C backend onto the physical robot to conduct real-world dynamic self-righting trials.
