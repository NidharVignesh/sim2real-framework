\section{Introduction}
\label{sec:intro}

Reinforcement learning (RL) can teach robots difficult skills, such as walking or getting up after a fall~\cite{hwangbo2019learning, rudin2022advanced}. The robot learns in a physics simulator, and the trained controller (the \emph{policy}) is then moved to the real robot. For large robots this last step is well supported: tools such as Isaac Lab/Orbit~\cite{mittal2023orbit} and Legged Gym~\cite{rudin2022advanced} expect a powerful on-board computer running Linux and ROS~2.

Small, low-cost robots are different. They use a microcontroller (MCU) such as the ESP32 (240\,MHz, less than 1\,MB of RAM, no operating system). Today, putting a trained policy on such a board is done by hand: the network weights are copied into C arrays and the sensor and motor code is written from scratch. Every change to the robot or the network means rewriting this code, and mistakes are easy to make.

We built \texttt{simtoreal}, an open-source Python library that does this step automatically. Our contributions are: (1) a converter that turns a trained Stable-Baselines3 or PyTorch policy into MicroPython bytecode (\texttt{.mpy}, the default), MicroPython source or a C header; (2) a generator that writes the complete on-board control loop (\texttt{main.py}) from a short YAML description of the hardware; (3) a test suite that checks the generated code against the original policy on a PC, in simulation and on a real ESP32; and (4) a test robot, \textit{Robo1}, with a MuJoCo model built from its CAD parts.

\section{Literature Review}
\label{sec:lit_review}

\textbf{Sim-to-real transfer:} The difference between simulation and the real world is called the \emph{reality gap}. It is usually reduced by training under many random physical settings (domain randomization, DR) and by measuring the real robot's properties (system identification)~\cite{tobin2017domain, tan2018sim}. Tan et al.~\cite{tan2018sim} randomized mass, delay and friction to make a four-legged robot walk; Hwangbo et al.~\cite{hwangbo2019learning} learned a model of the motors. GPU simulation~\cite{rudin2022advanced, mittal2023orbit} made large DR training fast, but the resulting policies run on ONNX or TorchScript, which need tens of megabytes of memory -- far more than an MCU has.

\textbf{Machine learning on microcontrollers:} TensorFlow Lite for Microcontrollers (TFLM)~\cite{david2021tensorflow} and MCUNet~\cite{lin2020mcunet} run neural networks on MCUs, but they are made mainly for image and speech tasks and use an interpreter with a reserved memory block (the ``tensor arena''), not for small control networks. RLtools~\cite{eschmann2023rltools}, a C++17 library, can even \emph{train} RL policies on an MCU, but the robot's environment must be rewritten in its own C++ system, so a policy trained with the usual Python tools (Gymnasium, Stable-Baselines3, PyTorch) cannot be reused directly. \texttt{simtoreal} keeps these Python tools and automates only the last step.

\textbf{Measuring the reality gap:} There is still no common benchmark for the sim-to-real gap on small embedded devices; Zhou et al.~\cite{zhou2026measure} found a large drop in performance when an agent trained only in simulation was run on cheap real hardware. We therefore test each step of our pipeline separately: is the generated code the same as the original, does it behave the same in a closed loop, and what does it cost on the device?

\section{Materials and Methods}
\label{sec:methodology}

\textbf{1) Taking out the policy:} The library opens a trained Stable-Baselines3 PPO file (\texttt{.zip}) or a PyTorch file (\texttt{.pt}). It keeps only the actor network (the part that chooses the actions): its weights $\mathbf{W}_l$, biases $\mathbf{b}_l$ and activation type. The critic, the optimizer state and other training data are dropped.

\textbf{2) Generating the network code:} For MicroPython, the network is written as a Python module and compiled on the PC into \texttt{.mpy} bytecode with \texttt{mpy-cross}. This is the default, because compiling the $\sim$60\,kB source on the board itself can run out of memory. For C, the weights become constant arrays stored in Flash, and a \texttt{policy\_forward()} function passes the data through the layers using two fixed-size buffers that swap roles after each layer. The C code never uses dynamic memory (\texttt{malloc}), so its memory use is known in advance.

\textbf{3) Generating the control loop:} The user describes the hardware in one \texttt{config.yaml} file. From it, the library writes \texttt{main.py}, which creates the sensor and motor drivers (e.g.\ an MPU-6050 IMU over I2C and SG90 servos), converts every reading to the units used in training (\texttt{scale}, \texttt{offset}), can give the policy the current value of an action as an extra input, applies each action directly or as a small step (\texttt{delta} mode) within limits, and repeats the read--decide--act loop at a fixed rate.

\textbf{4) Test robot (Robo1):} \textit{Robo1} (Fig.~\ref{fig:robo}) is a small robot that stands itself up after a fall. It has an ESP32, an MPU-6050 IMU and two SG90 servos. Its MuJoCo model uses the CAD shapes and measured masses of the real parts (94.8\,g in total), a joint range of $\pm 90^\circ$, a torque limit of $\pm1.0$\,N\,m and a damping of 0.02\,N$\cdot$m$\cdot$s/rad. The policy only uses values the robot can measure itself: $\mathbf{o}_t = [\phi_{\text{roll}}, \theta_{\text{pitch}}, a_z, q_1, q_2]$, where the vertical acceleration $a_z$ tells upright from upside-down and $q_1, q_2$ are the current servo targets. Each action moves a servo target by at most 0.08\,rad, 50 times per second. To test robustness, we randomize the body mass ($\pm15\%$), joint damping and friction ($\pm20\%$) and servo strength ($\pm15\%$, like a weak battery), and add sensor noise ($\sigma=0.015$\,rad).

\section{Results and Discussion}
\label{sec:results}
\enlargethispage{1.5\baselineskip}

\textbf{Is the generated code correct?} Our test suite (\texttt{tests/}, all results saved as JSON) runs the library exactly as a user would; Table~\ref{tab:verify} lists the results. The trained actor is a small network with 5 inputs, two hidden layers of 64 neurons ($\tanh$) and 2 outputs: 4{,}674 numbers, or 18.7\,kB as float32.
(i)~\emph{Same output on a PC:} we gave 4{,}609 inputs (2{,}000 random, 2{,}609 taken from simulated runs) to the original PyTorch network and to both generated versions. The largest difference was $1.2\times10^{-6}$ for MicroPython and $2.9\times10^{-6}$ for C -- only floating-point rounding -- and the final actions agreed in 100\% of cases. This test also found a bug: the generated C header did not compile for any network with more than one layer. After a one-line fix it compiles with \texttt{gcc -Wall -Wextra} and no warnings.
(ii)~\emph{Same behaviour in simulation:} the generated C code controlled the robot in 1{,}000 MuJoCo runs (5 start poses $\times$ 50 runs $\times$ normal and randomized physics). Success rate and time to stand up were identical to the PyTorch policy in every case.
(iii)~\emph{Same output on the ESP32:} on an ESP32 running MicroPython 1.28, the generated \texttt{.mpy} matched PyTorch for 20 test inputs.

\textbf{Cost on the ESP32:} The MicroPython policy file is 75.2\,kB, but once loaded it uses 119.6\,kB of the 162.3\,kB free memory -- 6.4 times the size of the weights -- because MicroPython stores every number as a separate object. One decision takes $155.2\pm7.4$\,ms (200 runs). The policy was trained to decide every 20\,ms (50\,Hz), so it is 7.8 times too slow and the loop can run at only about 6.4\,Hz. As every action is a small step, the robot would move about 7.8 times slower than in training, which changes the behaviour it learned. The MicroPython version is therefore correct, but not fast enough for this policy.

\textbf{Real sensor and servos:} We connected the IMU and both servos to the ESP32 (without the robot body). In a 500-cycle test, reading the IMU took 3.2\,ms and moving the servos 0.95\,ms -- together only 21\% of the 20\,ms budget -- while the policy took 182\,ms (98\% of each cycle; more than on its own because of memory clean-up), so the loop ran at 5.4\,Hz. With the sensor lying still, its noise was 1.3--1.6\,mrad (0.2\,mrad after filtering), about 10 times less than the 15\,mrad added in training, so the simulated sensor was pessimistic. The first generated \texttt{main.py} could not run the robot: it failed all four of our interface checks (pin numbers written as text, which the ESP32 rejects; only 2 of the 5 inputs; degrees instead of radians; and the raw network output sent straight to the servo). Adding $a_z$ to the YAML file alone did not help, so we improved the generator (Section~\ref{sec:methodology}). The new \texttt{main.py} passes all six checks, including one for a different, made-up robot, and ran unchanged on the ESP32 for 100 cycles (5.8\,Hz, again limited by the network).

\textbf{Simulation results:} Over 50 simulated runs per start pose, the robot stood up from all four standard fallen poses in 100\% of runs (in 1.36, 1.00, 1.26 and 0.78\,s) and from random falls, including upside-down, in 86\% of runs: 97.2\% overall, in 1.15\,s on average. With randomized physics, success stayed at 97.2\%, but standing up took 20\% longer (1.38\,s) -- something to check on the real robot.

\section{Conclusion}
\label{sec:conclusion}

\texttt{simtoreal} turns trained Stable-Baselines3/PyTorch policies into MicroPython or C code for microcontrollers and writes the control loop from a YAML file. Our tests show that the generated code gives the same results as the original policy on a PC, in 1{,}000 simulated runs and on a real ESP32, and they found bugs in both the C and the control-loop generators, which we fixed. On the real hardware, reading the sensor and moving the servos fit easily into the 50\,Hz budget, but the MicroPython network is about 9 times too slow. Next, we will make the MicroPython network faster or use the C header, and run self-righting tests on the assembled robot to measure the real sim-to-real gap.
